## 1. Executive Summary

Task 16 implements and proves a deterministic integration test harness in `crates/gateway/tests/model_registry_lifecycle.rs` covering the full end-to-end model registry lifecycle, error recovery, rollback invariants, and generation consistency under concurrent operations.

Key Invariants Verified:
1. Strict Offline-First Boot Order:
   - Embedded-only fallback boot when no cache/network exists.
   - Valid cached boot from LKG (`models-v1.signed.json`) with zero network dependency.
2. Monotonic Cryptographic Remote Updates:
   - Verified updates transition active source to `RemoteSigned` and persist atomically to disk cache (0600 mode).
   - Valid updates survive full offline process restart from disk cache.
3. HTTP 304 Not Modified Optimization:
   - Conditional request / 304 handling maintains existing active snapshot and LKG file hashes without churn or failure.
4. Resilient Stale Cache Offline Operation:
   - Network failure leaves valid LKG active, flags `stale: true`, logs error, and keeps cached models routable.
5. Absolute Hash Preservation on Rejections:
   - Every rejected update (tampered signature, incompatible schema, version downgrade, malformed JSON payload) leaves both the in-memory active snapshot hash and the on-disk LKG cache file hash 100% byte-identical.
6. Persistence Failure Isolation:
   - Interrupted persistence (e.g. read-only filesystem) prevents corruption and leaves prior LKG intact.
7. Concurrency & Generation Atomicity:
   - Multiple overlapping refresh triggers coalesce cleanly (`RefreshEnqueue::Coalesced`) with exactly one fetch in-flight.
   - Interleaved account additions and deletions during in-flight refresh publish consistent atomic snapshots without half-states or split-brain.
   - Thousands of concurrent readers observe generation consistency (`generation == registry.version()`) with zero split-brain pairings.
8. Zero Timing Luck & Dedicated Port Range:
   - All async synchronizations use explicit `tokio::sync::Notify` / atomics (zero sleeps or polling delays).
   - All network operations strictly target `127.0.0.1` on dedicated test ports 18876-18879.
   - Port 18876: Scenario 3 remote update server.
   - Port 18877: Scenario 4 HTTP 304 server.
   - Port 18878: Scenario 8 & 9 (mutex-guarded).
   - Port 18879: Dedicated offline port (no server listening).
   - All ports and temporary directories are completely released and cleaned up upon test completion.

## 3. Implementation: HTTP 304 Handling & Conditional GET

In `crates/gateway/src/registry/manager.rs`:
- Added `last_sig_etag: Arc<RwLock<Option<String>>>` and `last_cat_etag: Arc<RwLock<Option<String>>>` to `CatalogManager`.
- Enabled conditional GET via `If-None-Match` headers for remote signature and catalog requests.
- Added graceful handling for `StatusCode::NOT_MODIFIED`:
  - When server responds with 304, returns `Ok(self.current_snapshot())` without parsing empty body.
  - Updates `last_refresh_at = Some(now)` and sets `last_refresh_success = true`, `stale = false`.
  - Retains existing active snapshot and disk LKG without disk or memory churn.
- Updated ETag storage upon successful 200 responses.
